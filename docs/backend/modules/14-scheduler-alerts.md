# Module: Scheduler & alerts (`backend/src/scheduler/`)

User-authorized alerts and scheduled AI briefings — e.g. "外資連 3 天買超就通知我" or "每天收盤後給我
自選股的籌碼摘要". The scheduler is the user-authorized carve-out from the "no unattended agent"
rule (`backend/CLAUDE.md` §4, governance-as-code; bounds in §2): open to all signed-in users under
fair-use caps, event-driven, sponsor values masked. Why: users explicitly create every rule and
schedule, and the work is coarse, non-trading and quota-bounded.

**Status:** alerts v2 and scheduled briefings are implemented (below); §1 lists what is still open,
§9 what is built and not built.

**Implemented (backend, `scheduler/`):**
- **BYOK.** A scheduled run resolves the owner's own key exactly like an interactive turn
  (`accounts/byok.py`): with a saved key it runs on THEIR key and default model (`byok_scope`),
  is not held to the daily chat cap, and is recorded in the usage ledger with `byok=true`. If their
  keys don't cover the default model's provider the run is skipped and reported
  (`byok_key_required`), never moved onto the platform key. Every run (platform or BYOK) writes its
  model usage under a per-run id.
- **Which model a BYOK run uses.** A schedule job has no model field and no thread, so the owner's
  saved `users.default_model` is the only pick: honoured while it is still in the catalog
  (`llm/byok_catalog.py`) and its provider still has a key, else the `default_main` of the first
  keyed provider (`llm/byok_profiles.py`). `llm_usage` rows record the (provider, model) actually
  called and `byok`. Non-BYOK runs keep the platform profile via `resolve_role`.
- `triggers.py` resolves `next_run` (market events on trading days in the market timezone; 5-field
  cron with lists/ranges/steps); set on create and after every run. Pro gate removed; fair-use
  caps (`caps.py`, 409 `cap_reached`).
- `templates.py` + `evaluator.py` + the worker's `reconcile_alerts` / `handle_data_updated`:
  event-driven alert evaluation over the ingested Parquet store (read-only `SnapshotReader`), with
  per-`(capability, market)` watermarks (`alert_eval_marks`), edge-triggering via `state.met`,
  trigger modes, cooldown, expiry, watchlist fan-out, "never fire on data that predates the rule",
  and a fail-closed `check_output` guard on every body. **Implemented templates (all `public`
  data):** `close_price`, `daily_change`, `volume_surge`, `institutional_streak`,
  `attention_entry`, `disposition_entry`, `month_revenue_published`, `margin_balance_change`,
  `etf_premium_discount`, `material_announcement`. The legacy free-text `metric`/`threshold` model and the 60s price poll are
  removed.
- Fresh schema (no migration during dev): `alert_rules` v2 columns, `alert_preferences.timezone`,
  `alert_eval_marks`, `web` push platform. `GET /me/alert-preferences`, `POST /notifications/read`.

- `subscriber.py`: the daemon also consumes the live `data.updated` stream (Redis backend only; the
  in-memory bus cannot cross the ingest/scheduler process boundary) and feeds the same idempotent
  `handle_data_updated` path, resubscribing if the stream drops. Signal and sweep racing can never
  double-notify (watermark + dedupe key).
- Stored timestamps are UTC but round-trip **naive** on SQLite; engine code labels them UTC
  (`as_utc`) instead of calling `astimezone` on them.

**Frontend (web/):** template-first create form with fact-phrased preview and inline errors
(including the 409 cap), list with lifecycle status / last-fired / expiry, no Pro gate, and a real
notification inbox in the top-bar bell (badge refetched on window focus only, mark-read). Zod
schemas are contract-tested against real backend responses (`web/src/types/__fixtures__/`,
regenerated by `backend/tests/api/_gen_alerts_fixture.py`).

**Edit (done):** `PATCH /alerts/{id}` takes a partial `AlertPatch` — only fields sent are applied,
`null` clears a nullable field, `expected_version` mismatch is **409 `stale_version`**, unknown
fields (including scope) are 422. Every user edit bumps `version`; changing the condition resets
the edge-trigger `state`; re-enabling / re-conditioning / re-dating clears a prior auto-pause
reason. The frontend sends only changed fields, so an unchanged condition is never re-sent (which
would needlessly re-arm the rule). Engine writes (`save_alert_state`) do not bump `version`.
**Schedules (done):** `PATCH /schedules/{id}` is the same partial-edit contract (`SchedulePatch`):
`enabled`, `trigger`, `action`, `delivery_channels`, `quiet_hours`, `daily_limit`, with
`expected_version` → **409 `stale_version`** and unknown fields → 422. A new `trigger` (or
re-enabling a paused job) recomputes `next_run`; an unknown skill or unresolvable trigger is 422.

**Briefings (done):** the catalogue in `schemas/schedule_templates.py` (eight templates, §4) is the single source of
template → skill + trigger + which skill input carries the target. The Settings form and the chat
`propose_schedule` tool both draw from it, so nobody types a cron or a skill name. Every run is
appended to **one persistent thread per schedule** (`schedule_jobs.thread_id`, created on the first
run; a deleted thread is recreated), and the run's outcome is kept on the row (`status`,
`status_reason`) so the UI can say *why* a run was skipped or failed. A `running` mark older than
`RUN_TIMEOUT` (15 min) is treated as an orphaned run and the job becomes due again; a fresh one is
skipped, so a second poll never double-starts a run. A failed run is rescheduled to its next slot —
it is not retried on every poll. The run message spells out **every** skill input (`stock_ids`,
`stock_id`, `etf_id`, `symbol_id`…) — skills name their target differently, and dropping it would
brief on nothing.

**Chat entry point for schedules (done):** `propose_schedule` + the `schedule_proposal` card —
propose-only exactly like `propose_alert`; the model picks a catalogue template and ticker codes,
never a raw cron or skill, and the card posts the resolved `trigger`/`action` to `POST /schedules`.
Typhoon closures are not predictable and are not covered by `next_run` (see §5).

**Chat entry point (done):** the `propose_alert` tool + `alert_proposal` card (see
[03-tools](03-tools.md)). The agent only proposes; the user's tap on the card is the single
creation path, so bound 1 of §2 holds by construction. The rule vocabulary (`RuleCondition`,
`TriggerMode`, `describe`) moved to `schemas/alerts.py` so the tool and the scheduler share one
definition without an upward import (`scheduler` re-exports it).

**Dataset availability (verified against `ingest/jobs/` + `ingest/us_jobs.py`):** every ingest job
calls `publish_data_updated` after a successful write — the shared whole-market runner and each
bespoke job (attention, disposition, ETF NAV/AUM/expense, announcements, insider, US price/
fundamentals). The only silent writers are `job_us_symbol_universe` (a roster) and the derived
analytics jobs (`scoring_batch`, `trend_score_batch`, `screener_flags`), which no template reads.
**The ingest daemon binds the real publisher** (`ingest/publisher_binding.py`): the Redis transport
lives in `events/`, a layer `ingest` may not import, so the context builder resolves the
`INGEST_DATA_UPDATE_PUBLISHER_FACTORY` setting (`"module:callable"`, default
`events.ingest_wiring:build_data_update_publisher`) by name. It binds only on the Redis event bus —
an in-memory bus can't cross the process boundary, so the no-op is kept there — and any wiring
problem degrades to the no-op rather than stopping a pull. The signal still only lowers
latency: the per-pass reconciliation sweep remains the correctness floor for alert evaluation.

Price-derived templates read a **different dataset per market** (`TaiwanStockPrice` vs
`us_price_eod`); 法人, 注意股, 處置股 and 月營收 are Taiwan-only and `POST /alerts` refuses them for a US
symbol (422 `template_market_mismatch`; the form hides them and the agent tool rejects them).
**US symbols outside the screener universe:** `job_us_price_eod` also fetches every US symbol that
has an *enabled* alert (directly or via a watchlist-scoped rule), capped at 500 (deterministic,
truncation logged), so those alerts have data. Tickers are stored trimmed and upper-case. New
symbols have no history: `close_price` evaluates from their first ingested day, while
`daily_change` needs one prior day and `volume_surge` roughly half its window. A ticker that does
not exist upstream simply yields no rows — the user is not told.

**月營收 / 處置股 semantics:** 處置股 is a per-day snapshot list (presence in the day's partition;
absent from an ingested list is a real "not listed"; the alert also carries the disposal period).
月營收 is an event feed: a row counts only if its own date equals the evaluation day, so it does not
depend on the upstream returning a single day. **Not ingested at all** (no template can be built on
the "evaluate the ingested store" model yet): 暫停交易 (no ingest job) and `calendar_events` (fetched
per symbol through the router; its feed adapter does not exist yet) — 除權息 / 法說會 / 股東會 need
that data layer first. **Ingested and ready for templates:** 融資融券 (`margin_short`), ETF NAV /
折溢價, 主動式 ETF holding changes (sponsor).

## 3. Alert rules

```
AlertRule
 ├─ id, user_id, version
 ├─ scope: symbol (+market) | watchlist_id        # watchlist = fan-out over the group's items
 ├─ condition: {kind, params}                      # discriminated union, see catalogue
 ├─ trigger: once | once_per_day | every_occurrence, cooldown
 ├─ channels?, quiet_hours?, daily_limit?          # null = inherit AlertPreference
 ├─ explain: bool                                  # optional factual context note
 ├─ enabled, expires_at (default +90d), auto_paused_reason?
 └─ state {last_value, last_fired_at, fire_count}  # enables crosses_* / enter / leave
```

Thresholds are decimals. `expires_at` defaults to +90d and may be null ("never"); a null-expiry rule
auto-pauses after 1 year with no edits. A rule also auto-pauses on a spam threshold. UI status maps to
fields: 已暫停 = `enabled=false` or `auto_paused_reason`; 已過期 = `expires_at` passed; 已觸發 = a `once`
rule with `fire_count>0` (auto-disabled). `cooldown` is API-only (not exposed in the rule sheet).
A watchlist-scoped rule counts as **one rule** against the cap; its fires in one evaluation batch
are bundled into **one notification** (counts once toward the daily cap).

### Group scope vs per-stock levels

A watchlist-group rule applies **one condition to every member**, so it only makes sense for
conditions that mean the same thing for every stock: a percent move, a volume multiple, an
institution streak, a list entry, an ETF premium. A price level does not (2,475 vs 185), so
`close_price` (`schemas.alerts.PER_STOCK_KINDS`) is refused on a group — `POST /alerts` with a
`watchlist_id` returns 422 `template_scope_mismatch`. Price alerts are set per stock:
`POST /alerts/batch` creates one ordinary per-symbol rule for each item (its own stock, comparator
and level; frequency, lifetime and channels shared), all or nothing — the fair-use cap is checked for
the whole batch (409 `cap_reached`), duplicates and unsupported market/template pairs are 422, and
`origin_watchlist_id` (must be the caller's group) records where the batch came from, for display
only (`alert_rules.origin_watchlist_id`, no cascade). A group's per-member state is already kept in
the rule's `state.met` and is what the alert list shows when a group row is expanded. Note that
institution/margin/attention templates read datasets that need the vendor's sponsor plan; without it
those group templates are offered but will not fire until the data is ingested.

```
ScheduleJob

```

| 台股 ETF 完整分析報告 (`tw_etf_report`) | `etf-report` | weekly, Fri 15:30 |

| 處置/注意觀察 (`disposition_watch`) | `disposition-watch` | after_close |
| 事件週曆 (`weekly_catalyst`) | `catalyst-scan` | Mon 08:30 |

**Weekly watchlist review (`weekly_watchlist_review`).** The personal counterpart of the market-wide
morning brief and the stock-level `weekly_catalyst`: once a week the owner gets a short, descriptive,
data-grounded summary of THEIR OWN watchlist groups. It is built like the other skill-backed templates
(`schemas/schedule_templates.py` entry, a `ScheduleJob` running a governed skill through
`Orchestrator.run_skill`, the schedule's one persistent thread, an in-app notification that is a
160-character preview plus a deep link to the thread - the "summary + link" convention), with these
differences:

- **No tickers.** `takes_targets = False`; the action is `watchlist-review` with `inputs = {review: weekly}`
  (the skill's weekly mode). The trigger is a plain cron in Taipei time that the user composes from a weekday
  and a time (`POST /schedules` validates it like any cron: concrete minute and hour). The default is
  Saturday 09:00, after Friday's close in Taipei and New York. Settings and `propose_schedule`
  (`weekday` = mon..sun, `time` = HH:MM) both build it; the web form recognises the job by its skill input,
  not by an exact cron.
- **Numbers are code, not model.** The skill calls `get_watchlist_weekly_review` once ([03](03-tools.md)) and
  relays its finished `report`; the model may add one sentence but does not compute, reorder or drop a line.
  The week's move is `analytics/watchlist_review.py::weekly_move` over stored closes: the market's latest
  stored trading day against the last trading day on or before seven days earlier (Friday against the previous
  Friday; a holiday week moves both ends to the nearest trading day). Closes are unadjusted: a symbol with a
  split-like one-day break in the window is flagged, shown raw and kept out of the best/worst lists; a symbol
  with no close on either day is listed as "cannot compute" with the reason (suspended, newly listed, no data).
- **Events due in the next seven days** (the run day and the six after, inclusive): ex-dividend / ex-rights from
  the stored dividend dataset, shareholder meetings / cash-capital-increase record dates from the exchange
  calendar feed (the one router leg, bounded and reported when it fails), disposition periods starting or ending
  and who is under disposition or recently listed as an attention stock from the stored risk lists, and the
  statutory 財報 / 月營收 filing deadlines from `calendar/rules.py`. Each line carries its source and date. Not
  covered, and said so in every report: buyback windows, 法說會 dates, per-company report dates (no source),
  and the US event calendar beyond stored ex-dividend dates.
- **Freshness is stated, never omitted.** Per market: the data date, "older than expected" when the newest stored
  day is behind the last open day (scheduled calendar minus confirmed closures; a missing day is stale, not a
  holiday), and one line per unreadable or empty source.
- **Scope and caps.** All of the owner's groups, TW and US in separate sections, distinct symbols; at most 60
  symbols per run (the `get_my_watchlists` quote bound), shared evenly between the markets, with the true count
  and the number left out in the report.
- **Empty watchlist.** The worker checks before the quota gate and the model run: a user with no watchlist
  symbol gets one calm notice ("本週沒有可回顧的自選股…"), the job is `ok` with reason `nothing_to_review`, the
  cadence moves on, and no chat is spent.
- **Quota and keys** are those of every skill-backed schedule: a run counts against the owner's daily chat
  allowance (`UsageQuotaGate`) unless they run on their own key (their saved default model; the `byok_key_required`
  skip applies); it is not a platform-only job, so there is no `assert_no_byok_scope`. It counts toward
  `MAX_SCHEDULES` like any schedule and is open to every signed-in tier (the tool is `private`).
- Every string of the report passes `governance/textscan.py` (tests render each state through `check_output`);
  nothing in it ranks symbols to act on or suggests an action.

The four **full reports** are weekly on purpose: each run makes ~10 data calls and counts against the
owner's chat quota, and a five-year report does not change daily. The catalogue lives in
`schemas/schedule_templates.py` (one source for the Settings form and the chat `propose_schedule`
tool). The quick daily brief stays as its own light template.

**Report skills (prompt = the product).** `stock-report-tw`, `stock-report-us`, `etf-report` and
`compare-report` carry the section templates (識別 → 五年財務／報酬表 → 季節性 → 質性與風險 →
觀察摘要; the comparison report is 並列比較表 → 風險／獲利／季節性對照 → 特徵對照 → 差異摘要).
They call all data tools in **one parallel step** (a skill run has at most 8 model steps) and write
the report from pre-computed numbers. The computation is deliberately NOT in the prompt:

- `get_annual_fundamentals` — 5-year table (revenue, YoY, EPS, ROE on average equity, margins, debt
  and current ratio, FCF, dividends and yield). TW rolls FinMind's quarterly lines up to fiscal years
  (cash-flow lines are year-to-date, so Q4 is the annual figure); US uses Yahoo's annual frames
  (usually only ~4 years — the tool says so). A year in progress is marked and gets no ROE/yield.
- `get_revenue_seasonality` — growth-adjusted seasonal index (each period ÷ its own year's mean,
  averaged over complete years), peak/trough months and quarters, spread %. Needs ≥2 complete years;
  US quarterly data usually has fewer, in which case the report says so instead of guessing.
- `get_risk_metrics` — Beta (vs 0050 / SPY as the market proxy, named in the output), volatility,
  max drawdown, price return/CAGR. **Split-like price breaks are rebased first**
  (`analytics.risk_metrics.adjust_discontinuities`): TW limits a day to ~10%, so any larger move is a
  split (0050's 4-for-1 on 2025-06-18 would otherwise read as a −75% crash and corrupt Beta); US has
  no limit, so only ≥2:1 splits are caught. The rebased dates are returned and disclosed.
- `get_etf_annual_summary` — per-year price return, dividends (converted to the adjusted share basis
  with the ex-date's adjusted/raw ratio), yield and a simple total return.
- `get_comparison_metrics` — the side-by-side rows for two symbols, with **which side is stronger on
  each metric decided in code** from a stated direction (higher/lower is better); descriptive rows
  (seasonality, fund size, tracked index, premium, concentration) carry no verdict. **The table
  depends on what the two sides are** — an ETF has no revenue, EPS, ROE or debt, so:
  - *stock vs stock*: yield, dividend stability, revenue/EPS CAGR, seasonality + spread, ROE, debt
    ratio, Beta, volatility, drawdown, price return;
  - *ETF vs ETF*: tracked index/category, fund size, expense ratio (plus whatever part of the fee
    disclosure exists — several Taiwan ETFs publish a custody fee but no management fee), latest
    premium/discount, yield, dividend stability (split-adjusted), annualised simple total return,
    best/worst year, 1Y/3Y cumulative returns, holdings concentration (US), Beta, volatility,
    drawdown, price return;
  - *stock vs ETF*: only what both have (yield, stability, risk).
  An ETF is a Taiwan code matching `00xxx[A-Z]` or a US symbol with a fund profile. Dividend
  stability ranks by years paid, then by fewer year-over-year cuts, on a split-adjusted per-share
  basis so a split year is not a cut.

Charts come from declarative `chart_hints` (plural — one card, several charts) over the tools' own
series, rendered by the existing `GenericChart`. `hide_cards` in a skill's frontmatter drops the raw
key/value cards of identity tools the report only reads.

**Governance adaptations of the report templates.** The requested "最終建議：買進／觀察…",
"適合保守／積極型", 最佳買入／賣出時間, 整體推薦順序 and "只能選一檔請直接回答" are explicit
recommendations and are not produced. Section 五 is a data-based 觀察摘要: style traits by fixed
numeric rules, highlights and risks each citing a number, and a 0–10 risk score computed from four
stated components. The comparison's 優勢方 is per-metric only, and its 四、差異摘要 counts leads
without ranking or picking.

- Generated **at send time**, never pre-generated (stale briefings are the Gemini failure mode).
- Runs through `Orchestrator.run_skill` with the same guardrails as chat; appended to the
  schedule's persistent thread (not a new thread per run). Counts against the owner's chat quota.
- `next_run` is computed on create/update/run from the trigger against `TRADING_CALENDAR` and
  `market_closure` — no runs on holidays or typhoon closures. A sweeper resets jobs stuck in
  `running` past a timeout.

## 5. Engine

- **Which process:** one leader-gated evaluator inside the scheduler daemon subscribes (redis
  backend across processes; the in-memory backend only works if scheduler and API share a process).
  The dedupe key below is the multi-worker guard. The evaluator reads the store via the
  `MarketDataStore`/router seam (architecture §2), never Parquet/DuckDB directly.
- **Alerts:** subscribe to `data.updated` (`events/data_updates.py`, payload `{capability, market,
  as_of, scope}`). On each signal, load enabled rules whose template depends on that capability,
  evaluate **once per symbol** against the canonical store, fan out to rules/watchlist members,
  update `state`, emit notifications. Replaces the 60s poll. Per-user filters (entitlement mask,
  quiet hours, caps) are applied **after** fan-out and never cached across users.
- **Reconciliation (correctness floor):** `data.updated` is best-effort (a publish failure never
  fails ingest) and defaults to a no-op where no publisher is wired (the ingest context's default). A
  post-publication sweep evaluates any `as_of` with no watermark per `(capability, market)`
  (idempotent via the dedupe key). Every ingest job that feeds a template publishes today (see
  *Dataset availability* above), so the sweep is a safety net for a dropped signal or a daemon that
  was down, not a workaround for missing publishers.
- **Schedules:** the existing asyncio daemon (`python -m scheduler`, leader-gated) remains for
  time-based triggers; `due_jobs` now always has a `next_run`.
- **Holiday-aware `next_run`:** a market-event trigger (`pre_open`, `after_close`, …) skips weekends
  and the market's scheduled closures. `calendar/holidays.py` is a rule-based overlay (Taiwan public
  holidays minus commemorative days the exchange trades through, e.g. 孔子誕辰; the NYSE calendar for
  US) because the ingested-partition calendar only knows the past. Ad-hoc closures (typhoon days)
  are not predictable and are not covered. A **cron** trigger fires on the days it names regardless
  of holidays — the weekly reports are deliberately not holiday-gated.
- **Watchlist-scoped briefings:** a schedule may carry `inputs.watchlist_id` instead of a stock list
  (only `daily-context-brief`, the multi-stock TW briefing; the API rejects other skills with
  `watchlist_scope_unsupported`, and a list the caller does not own with `watchlist_not_found`). The
  worker expands it to the group's current Taiwan members (max 10) on **every run**, so editing the
  group changes the next briefing. An empty group ends the run as `error` / `watchlist_empty` and
  moves on to the next cadence. Alerts already supported `watchlist_id`.
- **Dedupe key:** `rule_id:occurrence_id:channel`, where `occurrence_id` is the event identity
  (date + event key), not merely the UTC date.
- **Quiet hours** are wall-clock time in the user's own timezone (`alert_preferences.timezone`,
  default Asia/Taipei; `PUT /me/alert-preferences` validates the IANA id). A rule/job window
  overrides the preference window. Behaviour differs by source: a **schedule** due inside the window
  simply stays due and runs on the first pass after it closes; an **alert** fires on time but its
  external-channel deliveries are recorded `payload.held = true` and not sent — the in-app entry is
  still written at once (silently). Each pass, `release_held` sends what is parked, for every user
  whose window has closed, as **one digest per user and channel** (「靜音期間的通知（N 則）」) and
  clears the flag. The inbox (`GET /notifications`, badge, mark-read) counts only `in_app` rows, so
  parked external copies never show up twice.
- **晨間摘要 (`morning_digest`).** For each opted-in user the worker sends one report per local day,
  on a Taiwan trading day, from 08:00 in the user's timezone (later if quiet hours are still running)
  until noon. It calls `get_morning_brief` directly for the market plus the user's own watchlist
  stocks/ETFs (max 5 TW stocks, 5 US stocks, 5 ETFs) and appends the result — text plus a
  `morning_brief` chart card — to the user's one 晨間摘要 thread
  (`alert_preferences.digest_thread_id`). The notification is the headline plus the top drivers
  (max 160 chars of preview for the inbox) and opens that thread. **No model call:** the report text
  is rendered by code (`tools/morning_brief_render.py`), so it costs no chat quota and cannot drift
  into advice. If the tool is missing or fails, the user gets the deterministic recap instead (what
  fired in the last 24 hours + active counts). Idempotent per `(user, local day)` via the delivery
  dedupe key.
- **In chat** the `morning-brief` skill calls the same tool once and reproduces its `report`
  verbatim (the model was found to add interpretation and a TL;DR when asked to write it itself).
- **`get_morning_brief`** (`tools/morning_brief_tools.py`) composes existing tools concurrently, each
  section isolated: US index strip (S&P 500, Dow, Nasdaq, SOX, VIX, 10Y, Fed rate), macro (USD/TWD,
  gold, oil, Fear & Greed), TAIEX and the TSMC ADR, three-institution net flows (外資/投信/自營商 in
  億元), breadth, best/worst three sectors, today's macro calendar in Taipei and ET, the user's
  stocks and ETFs (close, % change, TW ETF premium/discount), US trending and TW top gainers/losers,
  headlines (only market/economy headlines; any with trading language are dropped), and rule-based `flags` (VIX +15%, index
  ±2%, SOX ±3%, TSMC ADR ±3%, ETF premium beyond ±1%). A section that is empty, slow, gated or stale
  is named in `unavailable` and written as 「N/A」 — nothing is estimated. The TW table also
  carries 台指期夜盤（近月）: the latest night session of the front-month TAIEX future (single-month
  contract with the most volume; calendar-spread rows skipped), its close and % change against the
  previous day-session settlement, dated by the day the session ended. It is stated as 「前一夜盤交易時段變動」,
  is not a Top 3 Driver, has no flag, and is never worded as an implied open. Not provided: DXY,
  pre-market movers, and (in a dev store) anything the ingest has not loaded. TAIEX comes
  from Yahoo daily bars because the vendor's intraday TAIEX dataset rejects our plan. Charts
  (`chart_hints`): US index moves, institution net flows, best/worst sectors, and the watchlist's
  five-day indexed lines. **Top 3 Drivers** are the three largest moves on a fixed scale (index 1%,
  SOX 2%, ADR 2%, VIX 10%, 10Y yield 2%, net flow 50 億), each a fixed sentence template.
- **Journaling:** the worker publishes an event carrying its owner for every run and fire; the `event_bus` is not yet wired in composition (§1).
- Fair-use caps (per user, see [12](12-multi-user-tiers.md)): max alerts, max schedules, max
  notifications/day; exceeding returns 409 `cap_reached`. Counters use an atomic upsert /
  reserve-before-act (infrastructure §10). Over the daily notification cap, extra fires are **held
  into the next digest**, not dropped.

## 6. Delivery

One `NotificationEnvelope {title, body, facts[], locked_fields, deep_link, notification_id}` is
rendered per channel behind the existing `DeliveryChannel` protocol (`scheduler/delivery/base.py`).

| Channel | Mechanism | Notes |
|---|---|---|
| In-app | `notifications` row | bell inbox + unread badge + mark-read; same-batch fires bundled |
| Browser (`push`) | Web Push (RFC 8030) + VAPID (`vapid_public_key`/`vapid_private_key`/`vapid_subject`), via `pywebpush` in a worker thread | `/me/devices` with `platform=web`; the token is the JSON-encoded `PushSubscription` (endpoint + keys). The payload `{title, body, url, id}` is encrypted to the browser and shown by `web/public/sw.js`; a tap opens `url`. A 404/410 from the push service (or a token that is not a subscription) is reported in `DeliveryReceipt.stale_tokens` and the worker unregisters it. The permission prompt only appears when the user presses 「開啟」 on 設定 → 通知 |
| Email | Resend HTTP API (`resend_api_key`, `email_from_address` on a Resend-verified domain) | transactional (the user set the alert/schedule): plain text + a small accessible HTML copy (declared `lang`, `<title>`, escaped body), the non-advice footer, and the notification id as the `Idempotency-Key` so a retry after a timeout cannot double-send. Reachable when the account has an email. Bounces and complaints are handled (below), and every email carries a one-click unsubscribe |
| LINE | Messaging API push (`line_messaging_channel_access_token`; the older `LINE_MESSAGING_ACCESS_TOKEN` name also works) | recipient = the LINE user id from an explicit link (below), else the LINE sign-in id ([12](12-multi-user-tiers.md)); a push to someone who has not added the official account is a permanent 4xx receipt. **The free LINE plan caps messages per month (200 on the configured account) — a push over the cap fails with 429** |
| Telegram | bot API (`telegram_bot_token`, `telegram_bot_username`) | bound by the one-time-token flow below |

**Delivery is durable and retried.** The `notifications` row is both the dedupe guard and the
outbox. An external notification is committed as `delivery_state = pending` **before** anything is
sent, and its outcome is recorded after: `sent`, `failed` (not retryable, or out of attempts), or
still `pending` with `next_attempt_at` for a transient failure (a channel that raises counts as
transient). The delay doubles from 5 minutes up to 6 hours, with 6 attempts in all. Each scheduler
pass runs `retry_pending_deliveries`, which claims due rows (`FOR UPDATE SKIP LOCKED`, the claim
committed first so no lock is held across a network call) and also picks up a row recorded but never
sent because the process died in between (once it is two minutes old, so a live send is not raced).
A row therefore cannot be sent twice by a restart, and cannot be lost by a failure. The in-app entry
is `sent` from the start and never retried. Email's `Idempotency-Key` (the notification id) covers
the one gap left: a send that succeeded but whose answer was lost.

**One scheduler runs, and one worker takes a job.** The daemon holds a real lease (role
`scheduler`: a Postgres advisory lock, or a file lock on single-host SQLite; the same mechanism as
the ingest writer, [22](22-data-ingest.md) §6c). A second process stands by and takes over when the
first goes. Leadership alone is not trusted for correctness, though: a due job is **claimed** with
one atomic `UPDATE ... WHERE next_run <= now AND (status != running OR the run is orphaned)`, so
exactly one worker runs it even if two briefly both believe they lead. Failure is isolated to its
unit: each alert rule, morning digest and held-notification release commits on its own, so one that
raises loses only itself and the rest of the pass (and every other user's notifications) still run.

**Push endpoints are allow-listed (SSRF).** A browser subscription carries a push-service URL the
server later POSTs to, so `POST /me/devices` (web) accepts only `https` on the default port with a
host of the real push services (`fcm.googleapis.com`, `*.push.services.mozilla.com`,
`web.push.apple.com` / `*.push.apple.com`, `*.notify.windows.com`), and the channel re-checks before
every send (a stored token that fails is pruned, never called). The sender refuses redirects.
`delivery/push_endpoint.py`.

**Transports.** A channel shapes the request (`build_request`, unit-tested with no socket) and an
injected transport sends it (`delivery/transport.py`: `HttpxTransport`, `PywebpushSender`). Only the scheduler daemon builds channels with `live=True`; the API
process and tests never open a socket. A channel with no credential, or no transport, reports a
no-network success, so an unconfigured profile behaves as before. The transport classifies the
answer: network error / 429 / 5xx → `retryable`; any other 4xx (blocked bot, stale token) → permanent.

**Email suppression and unsubscribe.** `POST /webhooks/resend` (Svix-signed with
`RESEND_WEBHOOK_SECRET`; a stale timestamp or any bad signature is a 403, and with no secret
configured every request is refused) records an address in `email_suppressions` on a permanent
`email.bounced`, an `email.complained` or Resend's own `email.suppressed`; a soft bounce, delivery
or open is ignored. Recording is idempotent per address, so webhook redeliveries need no event
store. The worker never emails a suppressed address. Each email carries `List-Unsubscribe` +
`List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) and a visible link, both pointing at
`/api/v1/email/unsubscribe?token=<user id>.<HMAC of user id + current email>` — unforgeable, tied to
the account's current address, HTTPS only. `GET` shows a confirmation page (a mail scanner opening
the link must not unsubscribe anyone); `POST` unsubscribes (reason `unsubscribed`). Ticking 電子郵件
in settings again clears an *unsubscribe* (the user chose email again) but never a bounce or complaint.

**LINE linking.** `POST /me/channels/line/link` issues an 8-character one-time code (A–Z, 2–7; 10 min).
The user adds the official account (`https://line.me/R/ti/p/<basic id>`) and sends it the code; LINE
calls `POST /api/v1/channels/line/webhook` (the URL registered in the LINE console), which verifies
`X-Line-Signature` (base64 HMAC-SHA256 of the raw body with the Messaging channel secret, constant-time,
checked before the body is parsed) and binds the sender's Messaging user id in `channel_links`. The
same webhook replies with instructions on `follow`, confirms a link, and drops the link on `unfollow`
(a blocked account cannot be pushed to). Linking by code — rather than trusting the sign-in id —
works whether or not the Login and Messaging channels share a LINE provider. The webhook URL must be
reachable from the internet (locally: a tunnel such as ngrok to port 8000).

**Telegram linking.** `POST /me/channels/telegram/link` issues a one-time token (10 min) and returns
`https://t.me/<bot>?start=<token>`; the user taps Start, Telegram calls `POST /webhooks/telegram`
(authenticated by the `X-Telegram-Bot-Api-Secret-Token` header = `telegram_webhook_secret`, constant
time compare), and the handler swaps the token for the chat id in `channel_links`. The token is
single-use and expires. The operator points the bot's webhook at that URL with
`setWebhook(secret_token=…)` — `scripts/dev-backend.sh --webhook https://<public-host>` does it from
`backend/.env` (Telegram only calls public HTTPS, so locally use a tunnel). `GET /me/channels` reports which channels can reach the user now.

The webhook always answers Telegram with a 200 and talks back to the chat through the same
`OutboundTransport` seam the senders use (`get_telegram_transport`, overridable in tests): a
successful `/start <token>` is confirmed in the chat, and a bare `/start` (also `/start@<bot>`) or an
unknown, used or expired code gets the linking instructions. Other chatter is not answered. A failed
reply is swallowed; neither the bot token nor a chat id is logged.

**Telegram delivery.** One `sendMessage` per notification. A plain notification is plain text (no
`parse_mode`). A notification that carries a `layout` (`scheduler/delivery/layout.py`; today the 策略盯盤
messages) is sent as `parse_mode=HTML`:

- **Layout, not parsing:** `DeliveryNotification.title`/`body` stay the single plain source for the
  inbox, email, LINE and push and for the output scan. `layout` is a typed twin the same builder
  writes (`strategy_messages.morning_list_layout` / `hit_alert_layout`): blocks of a bold `head`,
  `lines`, and an optional `fold` that renders as one `<blockquote expandable>`. No text is parsed
  to recover structure. Every string goes through `html.escape` and the only tags are `<b>`, `<i>`
  (the footer) and `<blockquote expandable>`, so a stock name containing `&`, `<` or `>` cannot
  break the markup. Fixed copy only.
- **Scan coverage:** `safe_message` accepts a (body, layout) pair only when both the body and the
  text the layout renders (`render_text`, i.e. the HTML with its tags removed) pass `check_output`;
  otherwise the next candidate (the version without the quoted 重訊 subject) is tried, then the
  body alone without a layout, then the fixed line. What Telegram receives is therefore scanned the
  same as the plain body, and `NON_ADVICE_FOOTER` is always the last block.
- **Persistence:** only the Telegram `notifications` row stores `payload.layout` (the in-app row
  stays small), so a retry sends the same layout. A stored layout that no longer validates degrades
  to the plain text. A quiet-hours digest joins the stored plain bodies and has no layout.
- **Markup rejected:** a 400 whose description contains "parse entities" is answered once, in the
  same `send`, with the plain text (`formatted=False`) through the same `OutboundTransport`; that
  second answer is the receipt, so `_delivery_outcome` and the unlink-on-403 rule apply to it
  unchanged. There is no sleep. Any other 400 is final as before.
- **Length:** an HTML layout is trimmed on its blocks and rendered afterwards (`fit_html`): lines
  leave from the end of the last block, then empty blocks, then `…（完整內容請見 Miru）` is added.
  The first block and the footer stay, and a cut can never land inside a tag or an entity. Tags and
  entities count toward the limit, so it is conservative. If even the first block alone cannot fit,
  the message goes as plain text through the cut below.
- **Length (plain text):** Telegram rejects more than 4096 UTF-16 code units (an emoji counts two, a Chinese
  character one). `TelegramChannel.build_request` cuts a longer text at a line boundary (a single
  oversized line at a character boundary), then appends `…（完整內容請見 Miru）` and the non-advice
  footer, which always survives the cut. It never splits into several messages.
- **Open button:** with a public HTTPS app URL (`frontend_base_url`; plain HTTP or localhost gives
  none) the message carries an inline keyboard with one button 「在 Miru 開啟」, whose URL is the
  app origin plus the locale-less path `_push_url` derives from `deep_link` (`stock`, `thread`,
  `watch`; anything else falls back to `/settings/alerts`). The web proxy adds the locale prefix.
- **Unreachable chat:** the transport keeps the provider's JSON `description` of a 4xx (never
  logged). 403 (bot blocked or deleted, user deactivated) and 400 "chat not found" are permanent:
  the receipt is non-retryable with `address_gone=True`, and the worker unlinks the user's Telegram
  channel (`store.unlink_channel`) so Settings stops showing it as connected; the user links again
  from Settings. 429, 5xx, network errors and every other 4xx never unlink. Retry state stays in
  the database (`_delivery_outcome`); the httpx loggers are pinned above INFO so the bot token in
  the URL never reaches a log.

- **Precedence:** `AlertPreference` holds default channels, quiet hours, daily cap, morning digest;
  a rule/job may override and the UI shows inherited values.
- **Egress safety:** channel credentials are env-only; LINE/Telegram binding tokens are one-time;
  stored `line_user_id`/`telegram_chat_id` are encrypted at rest. Each outbound body is built with
  locked fields already nulled, then passes `guardrails.check_output`; a block falls back to a fixed
  template. **Legal review gates every external channel.**
- **Body text** is a fixed copy template. Footer: 「本通知為你設定條件的資料提醒，非投資建議。」
  AI-generated parts (briefings, explain-on-trigger) pass the chat output guardrail.
- **Tier lock on payloads:** delivery always happens. For non-entitled users a sponsor value renders
  as 馬賽克 in-app/push and as 「升級後可查看」 in email/LINE/Telegram, with one calm CTA.
- **Deep link:** `{route, symbol?, thread_id?, notification_id}` (unchanged from v1 push payload).

### 策略盯盤 subscription (`scheduler/strategy_store.py`, `strategy_messages.py`)

One subscription per user (`strategy_subscriptions`): the strategies (`volatility_squeeze`,
`oversold_bounce`, `ad_divergence`), every stock on today's screen or one watchlist group, whether to
get the morning list, and channels / quiet hours / daily limit (empty or null inherit the alert
preferences). `SchedulerWorker.run_strategy_watch` runs on every scheduler pass and reads only the
stored `strategy_watchlist` and `strategy_hits` partitions (module 20 §5c):

- **Morning list** once per trading day, before 13:30: each subscribed strategy's stocks with their
  key level (上軌 / 下軌 / 20 日低點) and the market breadth, then one 清單類股 20 日強度 line (the
  top three industries among the listed rows by `sector_strength_pct`, with their listed-stock
  counts; it describes the list only and is left out when no row has an industry), then one
  definition line per strategy on the list (`STRATEGY_DEFINITION`, the fact form of the screen
  rule). A condition alert ends with the definition of its own strategy. On Telegram the same facts
  are laid out for a phone: the list heading and breadth, then one bold block per strategy (name ·
  count) with one stock per line and `…另 N 檔，見 Miru` past the five shown, one industry per line,
  and the definitions in a collapsed 名詞 block. A condition alert names the stock and strategy
  once in its heading, then the check time, one bullet per condition, the background line, the 重訊
  subject, and the folded definition.
- **Condition alert** once per (stock, strategy, day) for the first slot the intraday check marked
  alertable, listing each condition with its observed and required value plus context (類股強度,
  法人 streaks, today's 重訊 subject). Slots from before a same-day subscription are not replayed;
  near misses are never sent; `daily_limit` caps condition alerts (the morning list does not count).
- Open to every tier (bound 2): a plan without intraday data (`tick_minute_k`) gets the alert with
  the intraday values masked. Bodies pass `check_output`; a flagged third-party subject is dropped,
  then a fixed line is sent instead.
- Recorded as `source='alert'` notifications with `source_id` prefix `strategy:`, so the inbox,
  quiet-hours hold, retry and dedupe (`strategy:{subscription}:{symbol}:{strategy}` per day per
  channel) are the alert machinery unchanged and no existing table needed a migration.

### 重大訊息 alert (`material_announcement`)

Reads the ingested `material_announcements` partition (forward-only daily dump from MOPS; no
per-user fetch). It is an **event**, not a state (`schemas.alerts.EVENT_KINDS`): the edge-trigger that
silences a state template while it stays true does not apply, so a filing today is never suppressed by
one yesterday (the per-day dedupe key still prevents double-notifying the same day). Only rows whose
`announced_date` is the evaluation day count, so a feed echoing older filings cannot look new.

**Third-party text.** The issuer's subject line is quoted as data inside a fixed sentence
(「公布 N 則重大訊息，最新主旨：「…」」): control characters and markup/link characters
(`< > [ ] ( ) \` * _ # \ |`) are removed and it is clipped to 40 characters. The finished body
still passes `_safe_body`/`check_output`; if the scan rewrites anything (routine buyback/disposal
subjects often read like trading language) the notification retries once WITHOUT the quote - still
saying that N filings exist - and only then falls to the fixed line. Quote marks and sentence
terminators in a subject are replaced by spaces, so it cannot break out of its quotation. One
notification per rule+symbol per day: the daily ingest writes one partition, and a later same-day
filing is not re-notified. It never characterises the filing and is never fed to
an LLM. **Keyword (built).** `material_announcement` takes an optional `keyword` (<= 20 chars): the rule
only fires on filings whose subject contains it (case-insensitive). It is the user's own text echoed
into the rule's title, so it is whitespace-normalised and refused if it holds markup/control
characters or trading language (the shared `schemas.memory_rules` scan). Media-news (`STOCK_NEWS`,
per-symbol, not ingested) is not built.

## 9. Status

Built (channels are web/browser, email, LINE, Telegram — no native APNs/FCM): holiday-aware `next_run`, watchlist scope (alerts and the multi-stock briefing),
quiet hours in the user's timezone with a held-notification digest, the 通知紀錄 history view, the
nonexistent-ticker warning, and real senders for LINE / Telegram / email (Resend) / browser Web Push (with Telegram
linking and a LINE add-friend link). **Also built:** the 晨間摘要 (see §5). **Also built:** `material_announcement` (MOPS 重大訊息, see below). **Not built:** media-news alerts, night-session futures / DXY / pre-market movers in the morning report, and a TW-ETF management-fee source (the exchange's ETF pages and SITCA do not publish
it in a machine-readable form, so the ETF comparison keeps showing the custody fee alone). The
external senders are covered by fake-transport tests only — none has been exercised against the
live provider, and legal review still gates turning any of them on in production.
